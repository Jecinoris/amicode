# Session-lineage mutation ledger for Files Changed

Status: proposed

Files Changed represents the declared session-visible work caused by one Session and its explicit spawned descendants. It must therefore be driven by provenance recorded at the mutation boundary, not inferred from Git state, filesystem watchers, or per-tool presentation metadata after the fact. A server-owned mutation ledger becomes the authority for session ownership, resource identity, operation outcome, and evidence availability. The ledger, its evidence store, retention, telemetry, and compaction are operational infrastructure and never recursively appear as Files Changed resources.

The decision is to issue a short-lived Mutation Context before every registered local mutation. The context binds the authenticated initiating panel and Session, root lineage, origin, exact operation, canonical endpoints, authorization, expiry, and idempotency or single-use semantics. The mutator writes an intent record, then commits or aborts an operation group containing one immutable Mutation Receipt per resource. Receipt facts record intent and execution outcome; append-only or derived Mutation Assessments separately record current observation confidence, net state, evidence availability, and expiry. Parent Sessions aggregate only registered task and session-spawn descendants; a fork begins a separate root. Ledger rows are owned by the root from creation and preserve a compact origin-session projection after child deletion.

Files Changed remains one file-first Work Column surface. Each touched canonical resource appears once and expands to its receipt history. A derived final state may be added, modified, deleted, reverted, or unchanged; execution and observation states separately represent failed, denied, aborted, partial, opaque, conflicted, and unavailable work. Text evidence is rendered as a bounded patch when safe. Binary, directory, redacted, conflicted, and unavailable resources expose truthful structured evidence instead.

Three alternatives were rejected. A global filesystem observer could notice more writes, but cannot reliably distinguish concurrent sessions or unrelated editor activity, creates an unacceptable surveillance boundary, and cannot cover remote tools. Continuing to add metadata to individual tools has lower immediate cost but repeats the bypass class whenever a new writer appears. Treating snapshots or watchers as ownership evidence reintroduces cross-session contamination; they are retained only to revalidate a receipt that already has an owner.

Known local mutators fail closed when they cannot participate in the protocol. A versioned mutator registry classifies every supported route as ledger-backed, opaque-with-unknown-receipt, or explicitly out of scope, and raw storage adapters do not accept unregistered session-visible writers. An opaque context has no declared local endpoint and can record uncertainty only; it cannot authorize a known local mutation. Inherently opaque shell, MCP, and custom actions remain usable but produce a visible unknown-side-effect receipt unless they emit declared resource receipts. Unowned local changes are never adopted into a Session merely because they occur during it; they can only make a known receipt conflicted or unavailable.

Receipt metadata is compact and lives with Session data; potentially large preimages and patches remain in a separate host-local evidence store with per-resource and per-session budgets. Root quotas, pagination, retention, and compaction bound receipt metadata as well; a known local mutation that would exceed capacity is denied before it changes storage. External and internal content are evidence-scoped. Physical targets are canonicalized before authorization and attribution, including symlink traversal and nonexistent leaf paths through their nearest existing parent. Safe traversal and revalidation are required where the provider supports them; a known local mutator on an unsupported provider is denied before mutation, rather than receiving a path-race claim. External baselines and sensitive internal values remain private to the Session, are redacted where necessary, are excluded from ordinary sharing, export, telemetry, and error serialization, and expire or are deleted with the root according to retention policy. A schema-owned field exposure matrix controls every such boundary.

The engine advertises a versioned full-provenance capability. Unsupported protocol discovery selects a legacy view without probing mutation routes. Mutation contexts remain server or extension-host local and never enter browser state, transcripts, logs, telemetry, shares, or errors; a missing, expired, revoked, wrong-owner, or invalid replayed context denies before filesystem access, while an exact idempotent retry returns its prior operation-group result. Opaque contexts have no local endpoints and emit an operation-level Unknown Mutation Receipt with no resource identity or patch evidence. Clients use the unified ledger only after negotiating the supported capability; pre-existing sessions retain a legacy view, and an already-open session can record only an explicitly labelled post-upgrade epoch. In-flight legacy work is never silently adopted. This requires coordinated fork release, verified binary pin, extension release, and overlay synchronization evidence rather than a client-only UI rollout.

Accepted costs are compact persistent receipt storage, bounded host-local evidence, a strict registration obligation for every local writer, explicit uncertainty for opaque tools, migration of generic file-writing APIs, partial-outcome semantics for inherently non-atomic filesystem operations, and a large end-to-end test matrix. The decision should be revisited only if Amicode deliberately adopts a platform-level audited execution sandbox with reliable process attribution; a broad watcher alone is not enough.
